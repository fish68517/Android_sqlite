# 新增功能开发思路和计划

日期：2026-04-22

## 1. 目标理解

根据 `doc/新增功能.txt`，本次新增需求的核心目标有两部分：

1. 通过 Android 侧能力获取健康数据，重点包括：步数、心率、血压。
2. 当健康数据出现异常时，触发通知提醒，并进行语音播报。

结合项目现状，我建议把这次需求定义为一个完整的“健康监测闭环”功能，而不是只做三个数据字段的展示。完整闭环应包含：

- 数据采集
- 本地存储
- 异常判定
- 通知提醒
- 语音播报
- 历史趋势查看
- 用户阈值配置
- 无法采集时的补录兜底

这样做的原因是：如果只接入数据采集，不补上异常规则、通知、历史记录和配置能力，功能会停留在“能看到数据”，无法形成真正可用的健康助手能力。

## 2. 结合项目现状的实际分析

### 2.1 当前项目已具备的基础

从代码结构看，当前项目并不是空项目，已经具备承接本次新增功能的基础：

- 项目结构仍然是 `MainActivity + 底部导航 + Fragment`，与原需求文档一致。
- 本地数据层已经用 `Room + SQLite` 实现，`LocalHealthRepository` 已经承担了主要业务读写。
- 已有登录注册、个人中心、AI 助手、健康打卡、用药提醒、健康看板等页面。
- 已有通知与提醒能力：
  - `MedicationReminderWorker`
  - `MedicationReminderScheduler`
  - `ExerciseReminderReceiver`
- 已有健康看板页面 `HealthDashboardActivity`，但当前主要是“手动运动记录 + 图表展示”。
- 2026-04-22 我已完成一次基线构建核验，当前工程可以产出 `app/build/outputs/apk/debug/app-debug.apk`。

结论：本次需求不需要从 0 开始搭架子，可以在现有项目上增量扩展。

### 2.2 当前项目与新增需求之间的差距

当前代码与新增需求之间，主要有以下缺口：

1. 还没有系统健康数据采集能力。
   - 目前的 `HealthDashboardActivity` 记录的是手动输入的运动类型、地点、时长。
   - 没有步数、心率、血压的系统读取能力。

2. 还没有“结构化健康指标表”。
   - 现有 `quick_records` 更适合简单打卡，不适合存储数值型健康指标。
   - 心率、血压、步数需要支持数值比较、趋势统计、异常判定、来源标记、时间范围查询，因此建议单独建表。

3. 还没有异常检测链路。
   - 当前提醒能力主要面向“定时提醒”，不是“数据异常提醒”。
   - 需要新增一套“读取数据 -> 判定异常 -> 记录告警 -> 发送通知 -> 触发播报”的流程。

4. 讯飞模块尚未真正可接入到当前工程。
   - `settings.gradle.kts` 目前只注册了 `:app`，没有注册 `:xfyun-speech-template`。
   - 根工程当前没有 Kotlin 插件配置，而讯飞模板是 Kotlin 模块。
   - 主工程当前是 Java 8 / `minSdk 24`。
   - `xfyun-speech-template` 当前是 Kotlin + Java 17 / `minSdk 26`。

5. 讯飞模板和新增需求之间存在能力不匹配。
   - `xfyun-speech-template` 文档和源码当前封装的是“语音识别”。
   - 本次新增需求里需要的是“异常时语音播报”。
   - 也就是说，现有模板不是 TTS 播报模块，不能直接满足“播报提醒”。

6. 讯飞官方资源目前不完整。
   - 按模板文档要求，应包含 `Msc.jar`、`jniLibs/libmsc.so`、`assets/iflytek`。
   - 当前模板目录里未发现完整的 `jniLibs` 和 `assets/iflytek` 资源。
   - 如果这些资源不补齐，后续即使代码接好了，运行时也会失败。

7. 数据库扩展存在潜在风险。
   - 当前 `AppDatabase` 使用了 `fallbackToDestructiveMigration()`。
   - 一旦新增表或修改表结构而不补正式 Migration，升级时会清空本地数据。

8. 当前项目存在中文编码异常。
   - 多个 Java/XML 文件中已经出现中文乱码。
   - 如果不先顺手治理，新加页面和通知文案会出现体验不统一、后续维护困难的问题。

### 2.3 关于“步数 / 心率 / 血压”真实可行的数据来源判断

这部分需要提前说明清楚，否则实施时容易出现认知偏差：

1. 步数
   - 可以通过 `SensorManager.TYPE_STEP_COUNTER` 获取。
   - 也可以优先从 Health Connect 读取更完整的聚合步数数据。

2. 心率
   - 标准 Android 提供 `Sensor.TYPE_HEART_RATE`，但并不是所有手机都有该硬件传感器。
   - 更现实的接入方式是优先读取 Health Connect 中已经汇聚的心率数据。

3. 血压
   - 普通手机标准传感器通常不直接提供血压采集能力。
   - 血压更适合通过 Health Connect、外部设备同步数据、或手动补录方式接入。

结论：

- 如果你要求“尽可能通用、尽可能贴近真实健康数据”，建议以 **Health Connect 作为主数据源**。
- 如果你要求“尽量少改工程、尽快先跑一个版本”，可以先做 **步数传感器 + 心率传感器可用则读 + 血压手动补录** 的降级方案。

## 3. 推荐实施路线

### 3.1 推荐路线：面向 Android 9 / Android 15 的统一方案

结合你前面的要求“最终运行在手机 Android 15 和模拟器 Android 9 上”，我建议采用下面这条主线：

1. 统一把新增健康数据能力建立在 `Health Connect + 传感器兜底 + 手动补录` 上。
2. 统一把异常提醒建立在 `Room + WorkManager/定时同步 + Notification` 上。
3. 语音部分拆成两类能力：
   - 语音输入：后续可以继续沿用现有系统语音输入或接入讯飞识别。
   - 异常播报：如果必须使用讯飞，则需要补充“讯飞语音合成/TTS”能力，不能直接复用当前识别模板。

这是我认为最稳妥的路线，因为它同时满足：

- 能覆盖 Android 9 与 Android 15
- 能兼顾步数、心率、血压三类数据
- 能落到“异常检测 + 通知 + 播报”的完整闭环
- 能与当前本地数据库项目结构兼容

### 3.2 推荐路线的关键技术决策

建议优先确认以下决策：

1. 是否接受把项目 `minSdk` 提升到 26。
   - 原因：Health Connect SDK 官方接入从 Android 8（API 26）开始更合适；讯飞模板当前也是 `minSdk 26`。
   - 这不会影响你明确要求的 Android 9 和 Android 15 目标设备。
   - 但会放弃 Android 7.x 的兼容。

2. 异常播报是否必须使用“讯飞 TTS”。
   - 当前模板只做识别，不做播报。
   - 如果必须全链路使用讯飞，需要补入讯飞语音合成 SDK 或扩展现有模板。

3. 血压是否允许采用“Health Connect / 外部设备同步 / 手动补录”的方式。
   - 如果要求“纯手机直接测血压”，那标准 Android 方案并不现实。

如果以上 3 点能接受，本项目后续实施会顺很多。

## 4. 建议的功能设计

围绕步数、心率、血压，我建议做成以下功能组合：

### 4.1 健康数据总览

在现有 `HealthDashboardActivity` 基础上升级为“健康数据看板”：

- 今日步数
- 今日最新心率
- 今日最新血压
- 数据来源状态
  - Health Connect
  - 设备传感器
  - 手动补录
- 最近同步时间

### 4.2 趋势图与历史记录

继续复用 MPAndroidChart，展示：

- 近 7 天步数趋势
- 近 7 天平均心率趋势
- 近 7 天血压变化趋势
- 异常记录时间线

### 4.3 异常提醒中心

新增一个“健康预警”入口，建议放在首页功能宫格或健康看板内：

- 查看最近异常记录
- 查看异常原因
- 查看处理建议
- 一键跳转到健康看板

### 4.4 阈值配置

建议新增“预警阈值设置”：

- 心率过高阈值
- 心率过低阈值
- 收缩压过高阈值
- 收缩压过低阈值
- 舒张压过高阈值
- 舒张压过低阈值
- 步数目标与低活动提醒阈值

默认可以先给出通用阈值，后续再结合用户年龄、病史、身高体重做个性化。

### 4.5 异常通知与语音播报

当检测到异常时执行：

1. 写入告警记录
2. 发送通知
3. 播放语音提醒
4. 点击通知可进入健康看板或预警详情页

播报内容建议保持简洁，例如：

- “检测到您的心率连续偏高，请尽快休息并关注身体状态。”
- “检测到血压数据异常，建议尽快复测，如持续异常请及时就医。”

### 4.6 数据补录与兜底

考虑到血压和部分心率数据并不一定能稳定从手机直接读取，建议保留手动补录能力：

- 手动录入血压
- 手动录入心率
- 标记来源为“手动”
- 手动数据同样参与趋势图和异常判断

这样即使 Health Connect 或传感器不可用，功能也不会完全失效。

## 5. 建议的技术实现思路

### 5.1 数据层设计

建议新增以下表，而不是复用 `quick_records`：

1. `health_metric_records`
   - 用于保存原始健康数据
   - 字段建议：
     - `id`
     - `userId`
     - `metricType`，如 `STEP` / `HEART_RATE` / `BLOOD_PRESSURE`
     - `valuePrimary`
     - `valueSecondary`
     - `unit`
     - `sourceType`
     - `sampleTime`
     - `createdAt`

2. `health_alert_records`
   - 用于保存异常告警
   - 字段建议：
     - `id`
     - `userId`
     - `metricType`
     - `alertLevel`
     - `alertTitle`
     - `alertContent`
     - `metricRecordId`
     - `handled`
     - `createdAt`

3. `health_alert_rules`
   - 用于保存阈值配置
   - 支持用户个性化阈值

说明：

- 血压需要两个值，建议 `valuePrimary=收缩压`、`valueSecondary=舒张压`。
- 步数、心率只需要 `valuePrimary`。
- `sourceType` 用来区分 `HEALTH_CONNECT`、`SENSOR`、`MANUAL`。

### 5.2 数据采集层设计

建议定义统一接口，例如：

- `HealthDataSource`
- `HealthConnectDataSource`
- `SensorHealthDataSource`
- `ManualHealthDataSource`

采集策略建议如下：

1. 步数
   - 优先 `HealthConnectDataSource`
   - 兜底 `SensorHealthDataSource`

2. 心率
   - 优先 `HealthConnectDataSource`
   - 如果设备确实存在心率传感器，再启用 `SensorHealthDataSource`

3. 血压
   - 优先 `HealthConnectDataSource`
   - 如果无数据，则允许 `ManualHealthDataSource`

这样做的好处是：后续如果你再接智能手表、蓝牙血压计，业务层几乎不用重写。

### 5.3 异常检测设计

建议新增 `HealthAlertEngine`，在每次新数据入库后立即执行判定：

- 步数
  - 当日步数过低
  - 连续多天未达成活动目标

- 心率
  - 静息心率过高
  - 静息心率过低
  - 连续多次异常时提升告警级别

- 血压
  - 收缩压过高/过低
  - 舒张压过高/过低
  - 连续异常时生成更强提醒

为了避免骚扰，建议增加去重策略：

- 同一指标在短时间内不重复弹多次
- 连续异常以“升级提醒”替代“重复提醒”

### 5.4 通知与播报设计

建议新增：

- `HealthAlertNotificationManager`
- `HealthAlertBroadcastReceiver`
- `HealthAlertWorker`
- `HealthVoiceBroadcastManager`

职责划分建议：

- `HealthAlertWorker`
  - 定时同步数据
  - 调用异常检测

- `HealthAlertNotificationManager`
  - 统一创建通知渠道
  - 统一发送健康异常通知

- `HealthVoiceBroadcastManager`
  - 负责播报内容拼装
  - 负责触发 TTS 播放

### 5.5 讯飞接入思路

这里需要特别说明：

当前 `xfyun-speech-template` 只能做“语音识别”，不能直接做“语音播报”。

因此语音部分建议分两步：

第一步，先完成模块接入基础工作：

- 在 `settings.gradle.kts` 注册讯飞模块
- 在根工程加入 Kotlin Android 插件
- 处理 `minSdk` / Java 版本兼容
- 补齐讯飞官方 SDK 文件
- 在 `Application` 中完成初始化

第二步，再决定播报实现方式：

方案 A，严格按讯飞方案做
- 补入讯飞语音合成 SDK
- 扩展当前模板为“识别 + 合成”统一模块
- 用于异常播报

方案 B，先交付可用版本
- 讯飞模块先接入语音识别
- 异常播报先使用 Android `TextToSpeech`
- 后续再替换为讯飞 TTS

如果从“先落地可用版本”的角度看，我更推荐方案 B；如果从“必须统一使用讯飞”的角度看，则要直接走方案 A。

## 6. 分阶段开发计划

输出物：

- 最终确认是否提升 `minSdk` 到 26
- 拿到讯飞 APPID 与完整 SDK 资源包

预计工作量：0.5 天

### 阶段 1：工程兼容与基础治理

主要内容：

- 注册 `xfyun-speech-template` 模块
- 增加 Kotlin 插件
- 对齐 Java 版本与 `minSdk`
- 检查 Android 9 / Android 15 权限策略
- 修复当前部分中文乱码文案

输出物：

- 工程可稳定编译
- 讯飞模块可被主工程识别

预计工作量：1 天

### 阶段 2：数据库与仓储层扩展

主要内容：

- 新增健康指标表
- 新增告警记录表

输出物：

### 阶段 3：健康数据采集接入

主要内容：

- 接入 Health Connect 读取步数 / 心率 / 血压

- 处理权限申请、可用性判断、无数据状态

输出物：

- 可视化健康看板完成

预计工作量：1.5 天

### 阶段 5：异常检测与通知链路

主要内容：

- 实现 `HealthAlertEngine`
- 实现告警写库
- 实现通知渠道与点击跳转
- 做提醒去重与降噪

输出物：

- 健康数据异常时可稳定收到通知

预计工作量：1.5 天

### 阶段 6：语音播报接入

主要内容：

- 完成讯飞初始化与封装
- 如果采用讯飞 TTS，则补充合成能力
- 如果先采用系统 TTS，则封装统一播报接口
- 与异常通知联动

输出物：

- 异常时可以播报提醒文案

预计工作量：

- 方案 A（讯飞 TTS）：1.5 到 2 天
- 方案 B（系统 TTS 过渡）：0.5 到 1 天

主要内容：

输出物：

## 7. 总体工作量预估

按照推荐路线估算：

- 如果采用“Health Connect + 系统 TTS 过渡播报”，总工作量约 **7.5 到 8.5 天**
- 如果采用“Health Connect + 讯飞 TTS 正式播报”，总工作量约 **8.5 到 10 天**

如果后续还要求：

- 血压外设对接
- 个性化阈值推荐
- 异常处置建议更智能
- 预警历史筛选与统计报表

则需要在上述基础上继续追加排期。

## 8. 当前建议的实施优先级

建议按下面顺序推进，而不是一次性同时铺开：

第一优先级：

- 工程兼容
- 数据库建模
- 步数 / 心率 / 血压采集
- 健康看板展示

第二优先级：

- 异常检测
- 通知提醒
- 预警记录

第三优先级：

- 讯飞语音接入
- 异常播报优化
- 阈值配置完善

这样做的原因是：先把“看得到 + 存得下 + 能判断”做实，再做“播得出 + 播得好”。

## 9. 我建议你本轮审核时重点确认的事项

请优先确认以下 4 个点，确认后我再进入实施会更高效：

1. 是否同意把项目 `minSdk` 提升到 26。
2. 是否接受“Health Connect 为主、传感器/手动为辅”的数据采集方案。
3. 是否接受“血压支持手动补录或外部同步兜底”，而不是要求手机纯原生直接测量。
4. 异常播报是否必须使用讯飞 TTS；如果不是必须，可以先用系统 TTS 过渡。

## 10. 结论

从项目现状看，这个需求 **适合继续做**，而且已有代码基础足以承接，不需要推翻重来。

但为了避免后续返工，我建议先按下面结论推进：

1. 先确认 `minSdk 26` 和 Health Connect 路线。
2. 先把数据采集、存储、看板、异常通知做完整。
3. 讯飞部分不要直接当成“播报模块”使用，需要单独补播报能力。
4. 数据库扩展时必须补 Migration，不能继续依赖清库升级。

如果你审核通过，我下一步会按照这份计划，先从“工程兼容 + 数据表设计 + 健康数据采集骨架”开始实施。
