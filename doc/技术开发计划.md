# 音乐播放器技术开发计划

## 1. 技术目标

基于 Android 原生 Java 技术栈，构建一个仅支持本地音乐播放的简体中文音乐播放器。项目采用 `MainActivity + BottomNavigationView + 多 Fragment` 的主架构，确保界面层次清晰、功能便于拆分、后续扩展成本可控。

## 2. 总体技术方案

### 2.1 架构方案

- 宿主页面：`MainActivity`
- 主导航：`BottomNavigationView`
- 主内容区域：`FragmentContainerView`
- 页面结构：首页 Fragment、音乐库 Fragment、歌单 Fragment、我的 Fragment
- 播放页：独立 Activity 或全屏 Fragment，首选独立 Activity，便于沉浸式播放控制
- 迷你播放器：作为主界面公共区域组件，随底部导航页面切换持续存在

### 2.2 开发语言与组件

- 语言：Java
- UI：Android View + XML
- 构建：Gradle
- 最低支持版本：建议保持 `minSdk 24`
- 列表：RecyclerView
- 本地数据库：Room
- 异步处理：先采用 `Executor + Handler` 或 `LiveData` 级别轻量方案
- 图片加载：Glide
- 媒体播放：MediaPlayer 首期可用；如果后续追求更稳定的音频焦点与通知控制，可升级为 ExoPlayer 或 Media3

### 2.3 首期建议

考虑到项目目标明确且为本地播放，首期优先保证功能闭环，不在第一阶段引入复杂框架。架构上保持“分层明确、实现适度”，避免过度设计。

## 4. 数据设计建议

### 4.1 核心实体

- 歌曲实体 `Song`
- 歌单实体 `Playlist`
- 歌单歌曲关联实体 `PlaylistSongCrossRef`
- 最近播放实体 `RecentPlay`
- 当前播放状态实体或内存模型 `PlayerState`

### 4.2 歌曲字段建议

- `id`
- `title`
- `artist`
- `album`
- `duration`
- `filePath`
- `albumId`
- `albumArtUri`
- `dateAdded`
- `size`
- `favorite`

### 4.3 数据来源划分

- 音乐元数据来源于 `MediaStore`
- 收藏、歌单、最近播放来源于 Room
- 用户开关配置来源于 `SharedPreferences`
- 歌词来源于本地 `.lrc` 文件

## 6. 关键技术点

### 6.1 本地媒体扫描

- Android 10 及以上优先使用 `MediaStore`
- 处理运行时权限申请
- 扫描动作放到后台线程
- 首次扫描完成后写入本地缓存表

### 6.2 音乐播放

- 统一封装播放器控制器
- 处理暂停、恢复、切歌、进度监听
- 处理播放完成后的自动切歌逻辑
- 统一维护当前播放列表和当前索引

### 6.3 歌词解析

- 读取歌曲同目录下同名 `.lrc`
- 解析时间标签
- 将歌词行与播放进度进行匹配
- 无歌词时展示默认提示

### 6.4 数据持久化

- 歌曲基础信息可按扫描结果缓存
- 收藏、歌单、最近播放必须持久化
- 当前播放模式与用户设置需要持久化

### 6.5 文案与国际化策略

- 本项目只做简体中文
- 所有文案统一放到 `strings.xml`
- 资源文件中直接写中文，不使用 `\u4e2d\u6587` 这类编码形式

## 9. 风险与处理策略

### 9.1 当前工程残留旧项目代码

现有仓库中仍残留大量与音乐播放器无关的旧业务痕迹，且当前工作区存在删除中的文件。正式开发前应先完成一次工程瘦身，避免命名、资源、依赖和包结构污染。

### 9.2 API 配置遗留

当前 `app/build.gradle` 中仍保留 SiliconFlow 相关配置。由于本期不接入 AI 与服务端，开发首阶段应移除或停用这部分配置，避免误用和密钥泄露风险。

### 9.3 本地媒体兼容性

不同 Android 版本在媒体权限和媒体库可见性上存在差异，需要在开发时优先验证 Android 10 以上设备表现。

### 9.4 歌词来源不稳定

本期只支持本地歌词文件，因此演示数据需要提前准备包含 `.lrc` 的歌曲样本。

## 10. 开发执行建议

审核通过后，建议按以下顺序正式启动开发：

1. 先完成工程清理与主架构重建。
2. 再完成本地扫描与音乐库展示。
3. 随后完成播放器核心能力。
4. 最后补齐歌单、歌词、设置与体验优化。

这样可以尽快形成可运行的最小版本，并降低后续返工风险。
